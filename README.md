# Intelligent Autoscaling for Cloud-Native Java Applications

---

## Overview

This project implements and evaluates two autoscaling strategies for a Spring Boot microservice running on Kubernetes:

| Strategy | Description                                                                                                                                                                                                                                    |
|---|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **HPA (Baseline)** | Kubernetes Horizontal Pod Autoscaler — reactive, **CPU + memory triggered**. The JVM holds committed heap, so memory stays high and the HPA resists scaling in — a documented finding showing why infra-level metrics poorly fit JVM workloads |
| **Predictive (LSTM)** | Custom autoscaler that forecasts load 60 s ahead with an LSTM, **plus a JVM-pressure floor** that adds capacity when GC pause / CPU pressure is high even when predicted RPS is low                                                            |

The key hypothesis is that **JVM-aware predictive autoscaling** can reduce SLA violations and resource waste compared to reactive CPU-based scaling, by acting on early signals in heap usage, GC pressure, and thread counts before latency degrades.

The predictive strategy is evaluated in **two arms** to isolate the JVM contribution:
**JVM-aware** (RPS forecast + JVM floor) and an **RPS-only ablation** (`--no-jvm-floor`).

The whole study is run in **two environments**: a local **Minikube** cluster (development
and the full local campaign) and a production-grade **Amazon EKS (Auto Mode)** deployment,
where pod scaling maps to real EC2 node provisioning and cost. EKS uses an **EKS-retrained**
model and environment-specific calibration — see
[Cloud Validation on Amazon EKS](#cloud-validation-on-amazon-eks-key-results) and the
[EKS runbook](k8s/eks/RUNBOOK.md).

## Key Results — Local (Minikube)

Minikube used `max_replicas=4`, a 35 RPS/replica calibration, and 123 thirty-second samples per
run. The bursty and GC scenarios are each a single corrected run (n=1); the spike scenario and the
RPS-only arms are n=2. The numbers below are the thesis **Table 5.4.1** (aggregated by scenario and
strategy); full per-run granularity is in Table 5.6.1. **SLA violations** = the % of 30 s intervals
whose p95 exceeded the 300 ms SLA. Read each row *within* its scenario (offered load differs by design).

| Scenario | Strategy | p95 median | p95 max | SLA viol. | Replica-hours |
|---|---|---|---|---|---|
| Bursty | HPA | 13.2 ms | 9 397 ms | 1.6% | 3.92 |
| Bursty | JVM-aware | 13.8 ms | 16 510 ms | 2.4% | 3.94 |
| Bursty | RPS-only | 16.5 ms | 204 500 ms | 26.8% | 2.65 |
| Spike | HPA | 15.6 ms | 40 713 ms | 15.9% | 3.93 |
| Spike | JVM-aware | 15.9 ms | **5 456 ms** | 17.5% | 4.01 |
| Spike | RPS-only | 16.4 ms | 28 400 ms | 26.8% | 3.72 |
| GC | HPA | 7.8 ms | 555 ms | 0.8% | 3.68 |
| GC | JVM-aware | 7.9 ms | **21.9 ms** | 0.0% | 3.88 |

>On Minikube the HPA and JVM-aware arms have *similar violation
> counts*, but the JVM-aware arm breaches far more **shallowly** — spike peak p95 **5 456 ms vs the
> HPA's 40 713 ms** (quantified as breach severity in Fig 5.5.3). The **forecast alone collapses**:
> the RPS-only arm (JVM floor off) rises to **26.8%** violations on both spike and bursty,
> because congestion suppresses the observed RPS so the forecast under-provisions — the JVM/CPU
> saturation **floor is what rescues it**. Cost *during load* is ~equal; the predictive cost win
> comes from **scale-in** (below), which the HPA structurally cannot do.

### Idle scale-in — the HPA pathology

The headline cost result is the dedicated **EKS 3-hour idle observation** (see
[Cloud Validation](#cloud-validation-on-amazon-eks-key-results)): the HPA holds **6** replicas for
three hours while the predictive arm returns to **1** — **20.4 vs 5.7 replica-hours (−72%, a 3.6×
gap)**. The **same pathology reproduces on Minikube**, where the HPA stays pinned at its 4-replica
ceiling at near-idle CPU: the JVM's committed heap keeps the memory-utilisation metric above HPA's
70% target even at zero load, so it never scales in. This idle over-provisioning — not scale-out
lag — is the HPA's principal inefficiency.

> **On GC-pressure** the JVM-aware arm removed the tail (Minikube p95 max 555 → 21.9 ms; EKS
> violations 4.8% → 0%). On EKS gc, though, the retrained forecast alone already reached 0%, so the
> floor *over-held* capacity (final replicas 4 vs the RPS-only arm's 1) — on EKS the floor is a
> targeted tool, not a universal necessity (§5.5.4).

### Forecasting model

Minikube forecaster at a 60 s (2-step) horizon, over 54 held-out test samples (1.3–144.6 RPS),
against two naive baselines (`analysis/forecast_quality.py` → `results/forecast_quality.json`):

| Model | MAE (RPS) | RMSE (RPS) |
|---|---|---|
| **LSTM** | 29.40 | 36.18 |
| Persistence (last value) | 22.23 | 35.04 |
| Moving average | 47.34 | 60.47 |

> The LSTM beats the moving-average baseline by ~40% RMSE but does **not** beat last-value
> persistence at this short horizon on periodic demand (it trails slightly on RMSE, more on MAE).
> Its value is enabling *proactive* scaling on cyclical load, not superior point-forecast accuracy.
> The **EKS-retrained** forecaster reaches **0.907** predicted-vs-actual correlation
> (MAE 0.137, RMSE 0.158 normalised; 64 epochs).

### JVM feature ablation

Forecast error with vs without the 5 JVM input features (mean ± SD over 5 seeds; 1-layer, 16-unit
net) — `analysis/feature_ablation.py` → `results/feature_ablation.json`:

| Feature set | MAE (RPS) | RMSE (RPS) |
|---|---|---|
| All features (incl. JVM) | 34.74 ± 2.12 | 44.07 ± 3.61 |
| Without JVM features | 33.84 ± 1.47 | 43.55 ± 1.63 |

> Adding the JVM features does **not** improve the workload forecast (difference within noise) —
> future RPS is externally driven. Their value is as **leading indicators of latency**: on the
> baseline runs CPU leads p95 by ~90 s (r = 0.45) and average GC pause by ~60 s (r = 0.36), ahead
> of the 30 s HPA reaction path. This is why the JVM signals drive the reactive **scale-up floor**
> (Fig 5.5.7), not the forecast.

## Cloud Validation on Amazon EKS (Key Results)

The study is reproduced on **Amazon EKS (Auto Mode)** with **two isolated clusters** (one
HPA arm, one predictive arm) so pod scaling maps to real node provisioning and cost, and
latency/node-hours are attributed cleanly per arm. EKS pods are materially weaker (the JVM
sees ~one core from the `300m` limit), so the run uses **environment-specific calibration**:
`RPS_PER_REPLICA` 35→**18**, `max_replicas` 4→**6**, control interval 30 s→**15 s**,
warm-up grace 0→**3 cycles**, and an **EKS-retrained** LSTM (larger: hidden 64, 2 layers).
Full write-up: [results/eks/EKS_RESULTS.md](results/eks/EKS_RESULTS.md); numbers in
`results/eks_analysis_summary.txt`.

### SLA violations — predictive ≤ HPA in every scenario (n=2)

| Scenario | HPA | Predictive (JVM-aware) |
|---|---|---|
| bursty | 8.7% | **2.9%** (≈3× fewer) |
| spike | 19.2% | **17.8%** |
| gc | 4.8% | **0.0%** |
| steady | 2.4% | 2.4% |

> Spike is a deliberate overload (~225 RPS peak exceeds six EKS pods), so both arms
> breach; the predictive arm still degrades more gracefully (lower p95 and count).

### Cost — the HPA idle pathology, amplified (RQ1/RQ5)

Dedicated 3-hour idle observation after a 15-minute load:

| | HPA | Predictive |
|---|---|---|
| Replicas after 3 h idle | **6 (pinned, never scaled in)** | **1** |
| Replica-hours over the window | **20.4** | **5.7** |

> Committed JVM heap keeps HPA's memory metric high, so it holds 6 replicas for 3 h at
> ~3% CPU. The predictive arm returns to a single replica within ~20 min — a **72%
> replica-hour reduction (3.6× gap)**, and under Auto Mode bin-packing those are real
> billable nodes.

### Forecast quality (RQ3) & ablation (RQ2)

- EKS-retrained LSTM reaches **0.907** predicted-vs-actual correlation on held-out test
  (MAE 0.137 normalised) — a genuine forecaster, not a mean-reverting constant.
- Ablation: on **spike** the JVM floor cuts violations below both HPA and RPS-only; on
  **gc** the retrained forecast alone already hits 0%, so the floor over-holds capacity.
  On EKS the floor is a **targeted** tool, not a universal necessity — *a better forecaster
  reduces reliance on the reactive floor.*

## LSTM Feature Set

The model is trained on 10 JVM and workload metrics scraped every 30 seconds.
All features are queryable from Prometheus at runtime — no post-hoc data required.

| Feature | Source |
|---|---|
| `request_rate_rps` | Micrometer HTTP counter |
| `response_time_p95_ms` | Prometheus histogram\_quantile(0.95) |
| `response_time_max_ms` | Micrometer HTTP max |
| `cpu_usage_percent` | Micrometer process CPU |
| `jvm_heap_used_bytes` | Micrometer JVM memory |
| `jvm_heap_utilisation` | Derived: heap\_used / heap\_committed |
| `jvm_gc_avg_pause_ms` | Derived: gc\_pause\_sum / gc\_pause\_count |
| `jvm_gc_pause_count` | Micrometer GC pause count |
| `jvm_threads_live` | Micrometer JVM threads |
| `replica_count` | Prometheus `up` job metric |

**Target**: `request_rate_rps` (2 steps ahead = 60 s forecast horizon)

JVM signals also drive the **JVM-pressure floor** in the live autoscaler
(`jvm_gc_avg_pause_ms`, `cpu_usage_percent`), independent of the forecast.

## SLA Definition

- **p95 response time < 300 ms** under all load scenarios — confirmed against the
  steady baseline via `ml/calibrate_capacity.py` before final runs (thesis §3.4.3)
- Scrape / control-loop interval: **30 seconds**
- Lookback window: **10 steps = 5 minutes**
- Forecast horizon: **2 steps = 60 seconds** (covers pod cold-start + readiness
  so scaling fires before capacity is needed)
